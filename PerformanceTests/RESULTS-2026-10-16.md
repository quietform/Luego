# Prepared-text reader measurement — 2026-10-16

The repeatable device benchmark is working. The current evidence does **not** establish sustained 60 fps throughout Luego or an improvement over the earlier implementation.

Production reader, services, and GRDB storage in an isolated benchmark app. Text fixture v1 contains 8,411 words in 80 fixed Markdown sections, with no images or network access. Each pass starts a fresh process and in-memory database, waits for rendered content at the top, then performs three fast swipes through deceleration. Normal reader progress tracking remains active.

Device: iPhone 15, iOS 26.6.1 (23G83), maximum refresh rate 60 Hz. Release `-O`, whole-module compilation, Xcode 26.0 (17A324), Swift 6.2 in Swift 5 language mode. Debugger detached, coverage/checker diagnostics off, automatic system attachments discarded. Measurement conditions attachment reports nominal thermal state and Low Power Mode off. Initial measurement used the paired network connection; diagnostic traces used USB. Traces were collected separately from measurements.

## Frame-count investigation

The zero values are present in XCTest's original console output and the legacy `ActionTestSummary.performanceMetrics` object, as well as the modern metrics JSON. JSON export is not introducing them. Apple's installed `XCTMetric.h` documents frame count as an animation signpost measurement, and [Apple's animation-testing session](https://developer.apple.com/videos/play/wwdc2020/10077/?time=395) describes it as counting displayed frames. The zero field is not documented here as an unavailable-value sentinel.

Four diagnostic controls use the same benchmark app, with two recorded passes after warm-up:

| Collector configuration | Reported FPS | Reported frame counts |
| --- | --- | --- |
| Custom `ReaderScroll` metric alone | 58.1369, 57.9844 | 0, 0 |
| Built-in `scrollingAndDecelerationMetric` alone | 58.1483, 58.2008 | 0, 0 |
| Custom metric, stable process, three intervals per pass | 58.1602, 57.7499 | 0, 0 |
| Custom metric, stable process, one interval per pass | 58.0112, 57.9911 | 0, 0 |

The first two controls restore the original fixture before every pass and perform three swipes. The last two launch before entering `measure` and retain that process across iterations, checking process-lifetime and repeated-interval effects. Their content position advances between passes, so they are counter diagnostics rather than repeatable content baselines. All fixture/completion assertions passed.

Together with the original combined-collector run and captured frame activity, this isolates the contradiction to the XCTest animation-measurement path on the installed Xcode 26.0 / iOS 26.6.1 combination. Removing `XCTHitchMetric`, keeping the process alive before/during measurement, and measuring only one interval do not resolve it. It is not specific to the custom category or scroll-phase signposts. The precise failure inside Apple's collector remains unconfirmed; this is not an Apple-confirmed defect or a claim that every exported metric is wrong. Treat the frame counter as unusable in this environment. Do not replace it with FPS multiplied by duration or a frame-lifetime count from another run.

A targeted search of Apple's documentation, release notes, and developer forums on 2026-10-16 found no documented match or workaround for this pattern. The [Xcode 12 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-12-release-notes/) describe unsupported animation metrics on simulators; that limitation does not explain these physical-device results. No toolchain change was made.

`validate_metrics.py` now rejects zero or missing `ReaderScroll` frame counts with a nonzero exit status. Its tests observed the invalid export pass before the guard was implemented, then verified rejection; a positive synthetic count remains accepted. This is a counter-validity check, not an absolute or relative performance gate. The diagnostic UI tests verify fixture movement and completion; their passing status does not validate the returned counters.

The diagnostic host has the same Mach-O UUID as the original benchmark. All regular repeats use the exact original signed products and normalized configuration. The production app and actor layout have not changed during this investigation.
